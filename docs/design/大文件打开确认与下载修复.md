# 大文件打开确认与下载修复

状态：已实现（2026-11-20；第二轮：聊天入口门控，实现中）

## 目标

1. 修复 PC Chrome 上较大文件（尤其 10MB 以上的 HTML）点击下载不可靠的问题。
2. 点击打开大于 10MB 的文件时，先提示文件过大，由用户选择"继续打开"或"直接下载"，避免整个文件被读入编辑器造成卡顿。
3. （第二轮）聊天消息里的文件引用打开同一门槛：打开动作本来就要发一次鉴权请求，补一个只返回大小的轻量端点，聊天/Git/命令面板的打开在载入前先问。

## 背景（问题证据）

- 前端所有下载动作统一经 `saveOrShareBlob`（`src/shared/utils.ts`）。它在 `<a download>` 点击后**同一任务内**同步 `revokeObjectURL`，而同文件的 `downloadBlob` 已注释说明"同任务 revoke 会取消下载（Firefox/Safari）"并用 `setTimeout` 延迟；Chrome 对大 blob 的下载启动同样可能被同步 revoke 取消，小文件不受影响——与大文件下载失败的观察一致。
- 桌面 Chrome 在 HTTPS 下支持 Web Share 文件共享（`navigator.canShare({files})` 为 true），`saveOrShareBlob` 会优先走 `navigator.share`，弹出系统分享面板而非直接下载；分享被取消（AbortError）时静默返回，用户感知为"下载没反应"。
- 打开大文件：点击文件树文件 → 整个文件以 JSON 读入 CodeMirror（`api.readFile`），20MB 级文档明显卡顿；HTML 预览再把整个内容塞进 iframe `srcdoc` 更重。
- 聊天打开入口（工具卡"open-file"动作、Markdown 链接）只有路径字符串；生成的独立 HTML 常落在外部只读目录（临时目录/Antigravity brain），路径解析规则与 `readTextFile` 相同但调用方拿不到大小。

## 方案

### 第一轮：下载修复 + 文件树门控（已实现）

1. `src/shared/utils.ts` — `saveOrShareBlob`：
   - Web Share 手递只用于触屏设备（`navigator.maxTouchPoints > 0`，覆盖 iOS PWA 这一最初动机）；桌面（无触屏）直接走经典下载链接，不再弹系统分享面板。
   - `revokeObjectURL` 用 `setTimeout(0)` 延迟，与 `downloadBlob` 保持一致。
2. `src/shared/constants.ts` — `LARGE_FILE_OPEN_BYTES = 10 * 1024 * 1024` 与 `LARGE_FILE_OPEN_LABEL`。
3. `src/modules/file-tree/FileTree.tsx` — `handleItemClick` 打开文件前，若 `item.size` 大于阈值，弹出确认框（复用删除确认框的样式）：继续打开 / 直接下载（走既有 `operations.handleDownload`，流式端点读原始字节）/ 取消。
4. 15 个 locale 的 `common.json` 增加 `fileTree.largeFile.*` 文案。

### 第二轮：聊天入口门控（本轮）

1. 服务端 `server/modules/file-tree/`：
   - 服务 `statFile(projectId, filePath)`：复用 `resolveReadablePath`（与 `readTextFile` 同一套项目/外部只读根解析与安全检查）定位文件，`stat` 后仅返回 `{ size }`；非常规文件报 400，ENOENT/EACCES 走既有 `mapFileSystemError`（404/403）。不读内容。
   - 路由 `GET /api/file-tree/stat?projectId=&filePath=`：thin route，解析两个必填查询参数后调用服务。
2. 前端 `src/shared/api.ts`：`api.fileStat(projectId, filePath)`。
3. `src/modules/file-tree/` 抽出共享对话框组件 `LargeFileOpenDialog`（文件树现有内联确认框改为使用它，经模块 barrel 导出），props：文件名、大小、下载中状态与三个动作回调。
4. `src/modules/project-workspace/hooks/useLargeFileOpenGuard.ts`：包在 `handleFileOpen` 外层的异步守卫：
   - 带 `diffInfo` 的打开（差异负载内嵌，不读盘）直接放行；
   - 否则调 `api.fileStat`，失败（403/404 等）直接放行——编辑器随后显示既有的加载错误；
   - 大小超阈值 → 弹 `LargeFileOpenDialog`：继续打开 → `handleFileOpen`；直接下载 → 绝对路径走 `readExternalFileContent`、相对路径走 `readFileBlob`，再 `saveOrShareBlob`；取消 → 什么都不做。
5. `WorkspaceMain` 接线：ChatInterface、GitPanel 的 `onFileOpen` 与命令面板 `openFile`、`openFileInEditor`（经 `useFileOpenResolver`）全部改走守卫；文件树仍用节点自带大小，不再发请求。

### 不变与取舍

- 编辑器内 HTML 预览按钮作用于已加载缓冲，选择"继续打开"后视为知情选择，不二次确认。
- 聊天每次打开多一次轻量 stat 请求（与既有 `useFileOpenResolver` 的搜索请求同量级）。
- stat 失败不拦截：路径解析失败的文件本来就会在编辑器里报加载错误，守卫不改变失败路径。

## 验证

- 服务端：`server/modules/file-tree/tests/` 新增 `statFile` 服务测试（项目内文件返回大小、越界拒绝、缺失 404、目录 400）与 `/stat` 路由测试（参数解析、转发、缺参 400）。
- 前端：守卫 hook 测试（小文件直接开、大文件弹框且三个分支正确、stat 失败放行、diffInfo 放行）；文件树 `largeFileOpenConfirm.test.tsx` 在对话框抽取后回归。
- `npm run test`（服务端）、`npm run test:client`、`npm run build`、`npm run typecheck`、`npm run lint`。

## 风险

- 触屏笔记本（Windows 等 `maxTouchPoints > 0`）继续走系统分享面板，属原平台行为不变。
- stat 复用读路径的解析规则，无新增授权面：能 stat 的路径一定也能被 `readTextFile` 读。
