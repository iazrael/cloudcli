# 恢复后台任务发送确认对话框

状态：已完成（feat/background-send-dialog，813 项聊天测试 + typecheck + build:client 全绿）

基准：2.19.0 / 2026-11-11

## 目标

恢复上游 #1583（`82a2b62a`）的对话框：会话回合已结束、后台任务（命令/子代理/工作流）仍在跑时，发送消息先询问，而不是现在的静默排队。fork 曾在 `108aa9b0`（v1.37.5 合并修复）中删掉了这个对话框；恢复它能让后续同步 upstream 不再反复撞这块。

## 方案

fork 与上游的排队机制不同（fork 由服务端持有排队消息），触发点按 fork 语义适配：

- **触发**：提交时 busy（`isInputBlocked ?? (isLoading || hasActiveBackgroundTasks)`）且非强制发送，若满足「busy 原因是后台任务、没有在途回复、没有已排队草稿」→ 弹窗。在途回复的判定沿用 `canForceSendQueuedDraft` 的同一写法：`processingSessions` 里该会话活动存在且 `background !== true`。
- **取消**：`restoreComposerAfterFailedSubmit` 原样退回文本与附件，不发送、不排队。
- **排队**：落入现有 `appendQueuedMessage` 静默排队路径；排队卡、追加、服务端自动补发与 force-send 逃生门全部不变。
- **仍要发送**：走直发路径，options 带 `forceInterrupt: true`（与排队卡强制发送语义一致；非 Claude 引擎以此新开回合并停掉后台任务）。
- **不变的两条既有行为**：在途回复期间发送仍静默排队（上游 #1634 同）；Claude held-process（`isInputBlocked=false`）发送仍直发并行、不弹窗（后台任务不会被停，弹窗文案的前提不成立）。
- **文案**：组件内联英文 defaultValue 兜底，en/zh-CN/zh-TW 提供完整词条，其余语言回退英文（fork 既有约定）。

## 风险

- 非 Claude 引擎选「仍要发送」会停掉后台任务——弹窗描述文案已明示，用户显式选择。
- `processingSessions` 缺失时（测试/异常场景）退化为按 `backgroundTasks` 属性描述任务，行为不变。
