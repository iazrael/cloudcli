## 批次三：消息排队

入口：前端 `src/shared/chatDrafts.ts`、`useChatComposerState.ts`、`useQueuedMessageSync.ts`、排队卡片和 API；后端 user、database 的草稿仓库、scheduled-messages 派发器及共享消息读取。

### 消息所有权与原子操作

- 服务端保存权威排队消息；追加、清空与草稿文本保存分开。草稿防抖保存不得写回本地队列副本，也不得因为本地为空删除另一个页面的队列。
- 追加在数据库事务内读写，与现有领取票据和派发竞争正确配合；领取后追加的内容留待后续派发，不能重复发送已领取内容。
- 文本按提交顺序以空行合并，附件按顺序保留，兼容已有 images 数据。发送设置延续当前前端合并行为，即后提交消息的设置用于整条合并消息；不要额外扩大允许的权限值或绕过 provider 校验。
- 已有或新增消息为斜杠命令时拒绝普通追加合并，保留输入并给本地化错误。检查领取失败后恢复与新消息竞争时的同类边界，避免恢复路径绕过命令不可合并规则。
- 请求成功但响应丢失时，不得盲目重试追加而重复消息。根据现有协议选择可验证的幂等处理或明确的失败确认方式，不引入无关队列框架。

### 旧页面兼容

- 列出所有草稿写入和删除调用方，包括旧 PUT 带 queuedMessage、空草稿 DELETE、重连与旧标签页请求。
- 为旧协议明确选择安全策略：能安全兼容则兼容；无法判断覆盖意图时显式拒绝并提示刷新，拒绝不得修改已存消息。不能把旧整份覆盖请求当作新追加请求，否则会重复已有内容。
- 新旧页面共存时，旧文本保存和旧删除不得覆盖、复活或删除新队列。保留可恢复的草稿输入；拒绝旧请求要有可追踪错误和明确用户提示。
- 不要求数据库结构迁移。确需结构迁移或无法安全兼容时，先给出证据及最小方案，由主代理判断是否需要追加批准。

### 前端顺序与恢复

- 同一 scope 的追加和清空按操作顺序执行；切换会话后，异步结果只修改原会话。
- 排队提交期间继续输入不得被清空；失败恢复到后续新文本之前，附件不丢失、不串会话。
- 保留各引擎的后台输入判断。Claude 经服务端准备原进程续轮，提交前领取消息，SDK 消费输入后确认；不能安全续轮则继续等待，不提供强制发送入口。
- hydrate、重连、跨标签页刷新遵循服务端权威消息，同时保留本地正在输入的文本和属于本页的浏览器 File 对象。

### 必须通过的验收场景

1. 连续追加 A/B/C，服务端保留正确顺序和所有附件。
2. 两个标签页同时追加，不互相覆盖；旧页面随后保存或删除草稿，队列仍完整。
3. 派发领取与追加交错、领取失败与追加交错，消息不丢不重；恢复顺序正确。
4. 追加与编辑、清空、重新排队交错，不删除新消息；失败时输入按原顺序恢复。
5. 上传或等待响应时切换会话、继续输入、附加新文件，数据各归其所属会话。
6. 斜杠命令单独排队可用，与普通文本不可合并；领取恢复路径也符合既定规则。
7. 文本防抖保存、hydrate、重连、隐藏页恢复不会复活已派发消息。
8. 现有强制发送、后台任务接续、队列派发事件回显和权限校验不退化。
