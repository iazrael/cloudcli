# ZCode 打断与发送改用 v4 命令

状态：已实现

## 目标与范围

修复 ZCode 会话在 cloudcli 里"打断不了、打断后发的消息被吞掉"的问题。只改 ZCode 运行时的停止、发送和本轮终态认领，不动网关和前端。

## 根因

引擎 0.17.1 会把后台任务完成通知排进会话自己的输入队列，当前一轮一结束（包括被打断），引擎就用队列里的通知自动开新一轮。这种轮次不是 `session/send` 开的，旧接口认不出它：

- 旧 `session/stop` 只中止 `session/send` 自己开的那一轮。通知开的轮次在跑时，它什么也不做（引擎日志 `hadActivePrompt: false`），cloudcli 却把运行记成已打断。
- 旧 `session/send` 先回"已接受"，再在后台交给引擎受理。通知轮次在跑时，受理被拒（`turn_not_steerable`）或被并进通知轮次后丢失，错误被引擎吞掉，消息不进库。

## 方案

- 打断用 `v4/command` 的 `stop`：引擎停掉当前任何前台轮次。回执 `accepted` 或 `noop`（本来就没在跑）都算停到了，其余状态按停止失败处理。引擎是同步停的，本轮 `resultType: cancelled` 的 `turn.completed` 会先于回执到达；停止已发出时，这个取消记为打断，不记为正常完成，否则被打断的任务会按"完成"通知；停止失败则撤销这个标记。消息还在被引擎受理（正在收尾被抢占的轮次）时点停止，先等受理回执再发停止（最多等 10 秒，超时照样停），否则停掉的是被抢占的轮次，用户这一轮随后照常开跑；运行还在准备阶段、消息没发出就点了停止，消息不再发出。
- 发送用 `v4/command` 的 `sendText`（cloudcli 刚建的会话除外，见下条），`requestedDelivery: 'startNow'`、`heldQueueDisposition: 'keepQueueAndSend'`：引擎抢占正在跑的通知轮次，立即开始用户这一轮，队列里的通知保留，之后照常送达。网关保证同一会话同一时刻只有一个 cloudcli 运行，所以被抢占的只可能是引擎自己开的轮次。回执不是 `accepted` 就报错，消息不再静默丢失。
- cloudcli 建的会话，在首条消息成功发出之前（按引擎会话记录，运行在建会话后、发消息前失败也算），消息仍走旧 `session/send`，并带上 `inputId`。引擎只在旧接口收到第一条输入时才把新会话写进库，这之前发 `sendText` 会因外键约束失败（实测）。全新会话没有后台任务，不存在会抢走消息的引擎轮次。旧接口会把 `inputId` 带进 `turn.started` / `turn.completed`，终态认领照样成立。
- `sendText` 的附件改成 v4 形状 `{ref, fileName, mime, bytes}`，`ref` 用上传文件的绝对路径，引擎把非 URI 的 ref 映射成本地文件，效果与旧 `localPath` 相同。模型参数 `modelSelection`/`modelExecution` 两边结构相同，原样放进 `sendText` 载荷。
- 终态认领：`sendText` 的命令 ID（旧接口则是随消息传的 `inputId`）就是这一轮的 `inputId`。引擎开轮时 `turn.started` 载荷带 `inputId`，运行据此记下自己的 `turnId`。`complete`/`error` 只有属于自己这一轮时才结束运行；带 `turnId` 但不属于本轮的终态（被抢占的通知轮次的取消、本轮开始前别的轮次结束）直接丢弃，不转发。还没认领、也不带 `inputId` 的终态推迟到本批引擎输出处理完再判：那时回执已到且仍未认领，算本轮提前失败（不能吞掉真错误）；否则算被抢占的轮次。事件不带 `turnId` 时按原规则处理。

## 验证

- 单元测试：`abort` 发 v4 `stop` 并按回执结算，回执前到达的本轮取消记为打断；新建会话首条走旧接口并带 `inputId`，首条没发成功的会话下次仍走旧接口；受理中点停止会等回执；未认领、无 `inputId` 的提前失败照常结束运行；`sendText` 载荷（投递方式、附件、模型参数）；回执被拒时运行报错；被抢占轮次的终态不结束本轮，本轮终态才结束。
- 实机：通过 cloudcli 的 ZCode 运行时连真实引擎复现"前台命令运行中、后台通知已入队"，打断后再发消息：第一次运行记为打断，第二条消息进库并得到回复。

## 风险

- 依赖引擎 v4 命令接口（0.17.1 已实测）。更老的引擎没有 `v4/command` 时发送会直接报错，不会静默失败。
- 打断后引擎仍可能立刻用队列里的通知开新一轮，这是引擎行为，桌面端相同；下一条用户消息会抢占它。
