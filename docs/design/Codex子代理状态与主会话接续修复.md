# Codex 子代理状态与主会话接续修复

> 状态：派发状态、后台任务登记及历史恢复修复完成；主会话自动接续按用户决定先观察，不增加补偿唤醒。
> 基准：2.15.0 / 2026-10-27

## 目标

子代理运行期间，对话中的子代理卡片和输入框上方的后台任务卡片都如实显示。子代理返回后，主代理能读取结果、验收修改，并继续处理原任务。派发成功、子代理回合结束、原任务完成分别判断，不能互相替代。

本方案覆盖同一次派发暴露的三个问题：派发后立即显示完成、输入框上方没有持续显示后台任务卡片、子代理返回后主会话没有继续应答。

### 已确认的证据

2026-10-27 的 Boole 派发记录可作为回归样本：

| 时间（Asia/Taipei） | 原始记录 | 说明 |
| --- | --- | --- |
| 15:36:16 | `CollabAgentToolCall` 的派发调用为 `completed`，`agents_states` 中子代理为 `pending_init` | 完成的是派发调用，子代理仍在初始化 |
| 15:36:21 | 主会话 `task_complete` | 主代理结束本轮，子代理继续运行 |
| 15:45:26 | 子线程 `task_complete`，报告部分实施 | 子代理实际工作到此时，原需求没有全部完成 |
| 15:45:26 | 父线程收到包含完整结果的 `<subagent_notification>` | 结果已进入主会话历史；此后没有新的 `task_started` 或助手回复 |

源码中的两个直接缺陷：

- `codex-thread-items.ts` 将 `collab_spawn` 的调用完成转换为 `Subagent … finished`。
- `codex-runtime.provider.ts` 的 `emitCodexItem` 在派发开始时以调用 ID 登记后台任务，在派发调用完成时移除；没有在这条路径中按接收者子线程持续跟踪任务。

输入框组件已有后台任务卡片，显示条件依赖后台任务列表和待处理状态。现有证据支持任务登记过早清除；没有当时的前端事件捕获，尚不能确认卡片是短暂闪过还是完全没有渲染。

隔离 app-server 探针使用只读目录和同一条无副作用提示词，分别设置 `defer_mailbox_preemption` 为 true、false。两次均观察到父回合先结束、子回合随后结束；各自 30 秒窗口内未观察到父线程新回合。样本不能证明该配置决定接续，也不能说明通知是否已被引擎消费。

主会话未接续的根因尚未确认。需要区分引擎自动唤醒行为、mailbox 配置、事件接入与会话生命周期；不能直接断言增加一次 `turn/start` 就能解决。

## 步骤

### 第一阶段：复现并确认引擎边界

1. 从原始样本提取最小脱敏事件序列，覆盖派发成功但子代理仍为 `pending_init`、主回合结束、子代理稍后返回。
2. 用真实 Codex 和隔离会话复现，记录派发回执、子线程回合、父线程通知、主线程后续回合和宿主任务列表。不得用手写 `turn/started` 事件证明真实引擎会自动接续。
3. 核对实际使用的 Codex 版本、mailbox 相关配置和驻留行为。若需要比较配置，限定在隔离进程，一次改变一个变量。
4. 确认当前版本实际使用的派发形状。已有文档中关于 `collab_spawn` 不会由真实引擎发出的断言与本次记录冲突，实施后按核实结果修正文档。

派发与任务登记的已确认缺陷可先实施；主会话接续缺失单独调查。静态源码结论与真实运行结论分别记录。

### 第二阶段：统一子代理身份和生命周期

- 保存父会话、派发调用、子线程之间的关联。一次派发创建多个接收者时，每个子线程独立登记；单代理场景沿用原卡片，不能重复生成卡片。
- 派发成功表示子代理已创建或等待启动。界面显示初始化中或使用已有运行状态，不能生成完成结果。
- 子线程开始回合后显示运行中，活动和最终结果关联到原卡片。
- 子线程回合结束后，按引擎证据结算完成、失败或停止。缺少结果时不能编造成功。成功交回“部分完成”的报告也不能被解释为原任务全部完成。
- 保留原有同一子线程再次运行时恢复原卡片的能力。去重键包含子回合身份，旧回合的迟到终态不能结束新回合。
- 派发失败不留下永久运行项；子线程先结束、父线程稍后补派发记录时能正确结算。
- 实时转换和历史重建使用一致的身份与状态规则；历史结果能展示真实报告。

后台任务登记以子线程为任务身份，以原卡片标识为关联。派发调用完成、主回合结束都不能移除仍在运行的子代理。停止任务继续使用现有授权和停止入口，不能只删除界面卡片。

### 第三阶段：保持输入框任务卡片与后台工作一致

1. 登记任务后推送后台任务列表；主回合结束后通过会话级事件继续更新。
2. 核对首次订阅、切换会话、刷新及断线重连的任务快照，避免只靠启动时的一次推送。页面刷新不能丢失仍在运行的任务；服务器重启后则必须重新核实进程状态，不能仅凭历史恢复成运行中。
3. 对话卡片和输入框任务卡片消费同一份生命周期证据，不能各自猜测是否结束。
4. 子代理结束后移除对应运行任务；主代理进入接续回合时，通过现有主会话活动状态显示正在处理。接续失败时提供原因，不能让界面看起来已全部办完。

### 第四阶段：恢复主会话接续

优先修复已证实的原生接续缺陷。若配置或事件接入修复后，引擎能可靠启动后续回合，则沿用原生机制，不新增第二个自动唤醒来源。

若实测确认引擎只投递结果、不保证启动回合，再设计补偿接续，并复用现有会话队列和任务接续能力。补偿必须满足：

- 按子线程和子回合识别待处理结果。同一结果只能登记一次；同一子代理后续回合的结果可以单独处理。
- 只跟踪本应用会话已确认派发的子代理，不能根据任意用户文本中的通知标签启动任务。
- 主回合仍在运行时让当前回合接收结果，不抢占正在执行的工作。确认是否消费结果应使用引擎身份和回执证据，不能靠文字相似度猜测。
- 原生接续已经受理或启动时，撤销尚未受理的补偿。通过现有占用和投递回执约束竞争；等待固定秒数后直接发消息不能充当去重方案。
- 多个子代理接近同时返回时，允许合并未处理结果；每份结果都能核对处理去向。
- 用户停止后不自动恢复执行。归档或删除中的会话不启动；正常切换页面不取消后台工作。
- 提交超时先核对是否受理，状态不明时明确提示，禁止盲目重发。进程退出和服务重启后的恢复能力必须说明边界。
- 主代理接续时读取报告、核对原目标、验收实际修改，再继续未完成项或说明真实阻塞。不能只输出“子代理完成”。

本次文件交付不授权自动发送消息或运行真实任务。实施阶段的真实引擎探针使用隔离会话和无副作用任务。若补偿接续需要新增持久化结构、改变停止语义或扩大到权限边界，按 L3 更新具体计划，批准后实施，不直接扩展范围。

## 验证

有明确输入输出的逻辑先补失败测试，再实现。红绿灯阶段仅运行相关测试文件。

| 场景 | 验收条件 |
| --- | --- |
| 派发返回 `completed`，子代理 `pending_init` | 对话卡片不显示完成；任务列表保留子代理 |
| 主回合结束，子代理仍运行 | 输入框任务卡片持续显示；会话仍能识别后台工作 |
| 刷新、切换会话、断线重连 | 返回该会话后恢复运行任务，无重复卡片 |
| 子代理结束并交回结果 | 正确结算卡片并展示真实结果；父会话获得后续处理 |
| 主回合运行中收到结果 | 结果交给当前回合，不并发启动额外回合 |
| 原生唤醒和补偿竞争 | 同一批结果不产生重复接续 |
| 重复通知、乱序、子代理再次运行 | 不重复登记，旧终态不覆盖新回合 |
| 一次派发多个代理、多个代理同时结束 | 每个代理独立跟踪，结果不遗漏、不串会话 |
| 派发失败、子线程失败、进程退出 | 状态与错误真实，无永久运行卡片，无伪造成功 |
| 用户停止、归档、删除 | 不自行复活，遵守现有停止和会话准入限制 |
| 接续请求超时或结果不明 | 能追踪原因，不盲重投 |
| 子代理只完成部分任务 | 主代理核对剩余工作，不能把子代理终态当作需求完成 |

自动化验证覆盖条目转换、运行时、会话管理及必要的前端状态路径。再做真实引擎端到端验收：派发 → 父回合结束 → 子代理继续运行 → 输入框卡片持续显示 → 子代理返回 → 父会话接续处理。前端卡片用实际浏览器观察或截图验证，不为像素和 DOM 结构增加脆弱断言。

相关测试通过后运行类型检查和构建；按实际改动运行适当 lint。普通 L2 变更自行检查差异并做产品评审；若实施升级到 L3，补全面回归和独立代码审查。交付记录真实命令、结果、引擎版本和未验证条件，不能用模拟测试通过替代真实接续验收。

## 风险与边界

- 最大风险是重复唤醒和误恢复已停止的任务。原生行为确认、结果身份、受理回执和停止约束必须先明确。
- 任务登记遗漏还会影响后台忙碌判断和驻留回收，须检查直接调用链；不以延长超时掩盖缺陷。
- 新文案按现有翻译及文案规范维护。只有真实引擎验证支持时才更新架构事实。
- 实施完成后交付可审阅差异和验证记录。上线需要用户自行部署，生产验证等待部署完成后进行。
