# 刷新页面后的事件重放游标

## 状态

已实施，待验证。

## 目标

刷新页面后，正在运行的会话只补发刷新期间错过的事件，不再把当前 run 的全部历史事件从第一条开始重放。

## 现象与根因

会话 `ses_e3481e2f2ffe1PmWvz81hgwO5t`（opencode，`合并上游`）从 2026-11-11 16:43 起只有一个用户提问，之后的 367 条 assistant 消息都属于同一个仍在运行的 run。每次刷新页面：

1. 前端的重放游标 `resumeSeqs` 只存在内存里，刷新后归零；
2. `chat.subscribe` 因此发送 `lastSeq: 0`；
3. 网关对运行中的 run 从缓冲第一条开始补发（`chat-websocket.service.ts` 的 `if (isProcessing) for (const event of replay.events)`）；
4. 这个 run 的缓冲覆盖整段 1.5 小时的对话，客户端于是把整段内容从头发送一遍。

完成态 run 不重放（走 REST 历史），所以只有「刷新时仍在跑」的会话会触发。长回合（agent 连续工作很久、中途不结束 run）会把整个 run 都变成「从开头加载」。

## 方案

把已应用的传输游标持久化到 `sessionStorage`，按标签页隔离：

- `SessionTimelineStore` 在 `applyServerEvent` 收到带 `seq`/`streamEpoch` 的帧时，更新模块级游标表；每累计 25 个序号或 `pagehide` 时写入 `sessionStorage`，最多保留最近 50 个会话。
- 刷新后新 Store 从 `sessionStorage` 读回游标，`chat.subscribe` 带 `lastSeq` 与 `streamEpoch`；代次一致时网关只补发游标之后的事件，代次变化（服务端重启）由现有 `stale` / epoch 逻辑退回完整重放 + REST 对账。
- 只持久化实际经过 `applyServerEvent` 的帧，不持久化 `chat_subscribed` 的权威水位：确认里的 `lastSeq` 可能领先于尚未应用的重放事件，把它当游标会跳过缺口。
- 写入失败、存储损坏或无 `sessionStorage` 时静默退回旧行为（内存游标 + 刷新后完整重放）。

已知边界：如果刷新时某个 assistant 消息正在流式输出、且该引擎要到消息完成才落盘（Claude/Codex 类），刷新后会先看到已落盘的部分，当前正在生成的那条消息在完成前可能缺失；opencode 在 run 中持续写库（含 `state.status: running` 的块），历史页本身已覆盖进行中的内容。该边界不影响本次现场，后续如需恢复「进行中的半条消息」，应持久化未落盘的流缓冲，而不是重新扩大重放范围。

## 验证

- Store 单元测试：应用帧后刷新（重新导入模块）读回游标；`chat_subscribed` 水位不推进持久化游标；epoch 变化重置游标；损坏的存储被忽略。
- 订阅帧包含恢复的 `lastSeq` 与 `streamEpoch`。
- `npm run test:client`、`npm run typecheck`、`npm run build:client`。

## 风险

- 跨标签页不共享游标（`sessionStorage` 按标签隔离）：另一个标签页首次打开仍会完整重放一次，这是有意的安全选择——不同标签页的应用进度不可互相证明。
- 服务端重启后代次变化，客户端退回一次完整重放，与现状一致。
- 正在流式输出且尚未落盘的消息可能短暂缺失（见上）。
