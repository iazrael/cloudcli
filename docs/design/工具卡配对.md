# 工具卡跨路配对（阶段 4）

> 状态：已实施（2026-09-18）
> 目标：弄清"工具卡重复/不配套"的成因，区分可修的与结构性的

## 勘察结论

`toolIdentity.ts` 的匹配顺序是：精确 `toolId` → 完整调用指纹（工具名 + 完整入参）→
Edit 的窄路径。其头注释已经写明两路的 `toolId` 各自推导、可能不同。逐家核对如下。

### claude：两路本来就一致，无需改动

历史与实时都走 `normalizeMessageRows`，`tool_use` 块的 `toolId` 都取 `part.id`
（Anthropic 的 `toolu_…`）。精确匹配可用。

### codex：两个 id 空间无法调和，这是结构性的

| 路径 | toolId | 来源 |
| --- | --- | --- |
| 实时 | `itemId` | SDK `item.id` |
| 历史 | `callId` | rollout 的 `payload.call_id` |

SDK 的 `CommandExecutionItem` 类型**只有 `id`，没有 `call_id`**
（`node_modules/@openai/codex-sdk/dist/index.d.ts`），所以实时侧拿不到 `call_id`；
而历史侧的 `call_id` 是 function_call 与 function_call_output 的配对键，不能改用 `payload.id`，
否则工具结果就配不上自己的调用。

**结论：Codex 工具卡的精确 id 匹配永远不成立，只能走指纹。** 这不是遗漏，是两侧 id 空间不同。
不要再试图用 id 修它。

### codex 指纹对不上（已用真实会话验证）

样本：一次 MirLite 调光会话的 rollout（1406 行，173 次工具调用，124 个命令执行）。

**成因一：命令文本两路不同（影响每一张 Bash 卡）**

| 路径 | `toolInput.command` |
| --- | --- |
| 历史 | `sed -n '1,240p' …/SKILL.md`（从脚本里解析出的 `cmd` 实参） |
| 实时 | 整个 `command` 数组 `["/bin/zsh","-lc","sed -n '1,240p' …"]` |

指纹因此必然不等；加上两侧 id 空间本就不同，**精确匹配与指纹同时失效，每条命令渲染两张卡**。

在样本上比对候选字段，取 shell 包装的**最后一段**与历史侧逐字相等：

| 候选 | 相等比例 |
| --- | --- |
| `command[最后一段]` | **50/50 = 100%** |
| `parsed_cmd[0].cmd` | 29/50 = 58% |

`parsed_cmd` 会把复合命令（`pwd; test -d … && …`）拆成多条，而历史保留整串，所以它不对。

**成因二：多命令脚本粒度不同**

含 2 条命令的脚本（`call_VuxhuYZoDEatTu0DlbLdbsDI`）实测：历史 1 张卡（命令换行拼接），
实时 2 个 `CommandExecution`。样本里 162 个脚本中有 3 个是多命令。

实时侧**没有父脚本 id**（item 只有自己的 `exec-<uuid>` 与 `turn_id`），
所以"按脚本合并"没有可靠分组键，只能由历史侧拆开对齐。
适配器的子代理路径（`:1057`）本来就是**每个操作一行**，只有主历史路径（`:1682`）合并——
拆开同时也让适配器自洽。

## 方案

1. **实时命令文本取 shell 包装的最后一段**，与历史侧解析结果对齐。解决成因一。
2. **主历史路径按操作拆行**，与子代理路径一致。解决成因二。

两步都用适配器层测试钉住"同一次调用两路产出等价的卡片集"。

## 实现说明

实时侧的命令字段在两种序列化下形状不同：rollout 的内部事件里是数组
`["/bin/zsh","-lc","<cmd>"]`，而 SDK 的类型声明写的是 `string`。
`readCodexCommandLine` **两种都处理**——数组则取 shell 标志（`-lc` / `-c`）之后的部分，
字符串则原样返回——所以不依赖哪一种序列化到达，也不需要事先确认。
