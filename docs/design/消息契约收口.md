# 消息契约收口（阶段 1）

> 前置：阶段 0「时间线排序权威化」已实施

## 现状勘察

阶段 0 之后重新量了一遍，结论比预想的更糟，也更好修。

### 所谓「一套标准」其实有两份，且已分叉

`NormalizedMessage` 曾有两处独立定义——`server/shared/types.ts` 与 `src/shared/types.ts`。
**七个线上字段只有一端声明**：`actualSessionId`、`exitCode`、`parentToolUseId` 只在前端，
`isCancelledError`、`memoryCitations`、`reason`、`toolUseResult` 只在服务端。
服务端那份用 `[key: string]: unknown` 兜住缺口，所以从不报错。

漂移是双向的，而且不止于字段有无：`images` / `files` / `subagentTools` 在一端是 `unknown`、
另一端是精确形状；`toolResult` 一端可空一端不可空。

`parentToolUseId` 最能说明问题——它由 `claude-runtime.provider.js` 实际产出，
但那是 `.js` 文件而 `checkJs: false`，**TypeScript 从未检查过它**，于是服务端类型里可以一直缺着。

`ServerEvent` 另有两份逐字重复的定义（`src/shared/types.ts` 与 `WebSocketContext.tsx`），
且 `kind?: string` 等于没有类型。

### 索引签名的代价远比想象小

实验：删掉索引签名后全量 `typecheck`，服务端 9 处报错，**全部是同一类：真实存在的契约字段从未声明**。
不是 403 处调用点要重写。索引签名掩盖的是声明缺失，不是设计弹性。

前端的 `NormalizedMessage` 本来就没有索引签名——它的松散之处在 `ServerEvent`。

### 合流的通路是现成的

根级 `shared/` 目录已经存在（`shared/networkHosts.js`），
且**两个 tsconfig 都已经 include 它**，`server/index.ts` 已在跨端引用它。
不需要改构建配置、不需要动 Vite 别名。

## 切片

### 1a 一份契约，且让类型说实话（本次提案）

把**协议类型**（服务端↔客户端的线上格式）抽到根级 `shared/`，两端各自 re-export，删掉重复定义。

只抽协议部分：`server/shared/types.ts` 依赖 `node:http` / `node:stream`，
`src/shared/types.ts` 依赖 `react` / `i18next`，两份都是「协议类型 + 本端专属类型」的混装，
搬的是交集那一层，各端专属类型留在原地。

同一次改动里：

- 逐个裁决那 15 个漂移字段——该进协议的进协议，该留本端的留本端，不再靠索引签名互相兜底
- 删掉 `[key: string]: unknown`，把 38 处报错对应的字段显式声明
- `kind` 与 `ServerEventKind` 也统一到这一份，消灭第二处枚举

做完之后，任何一端新增字段而不声明会**编译失败**——这是「牙齿」的第一颗。

### 1b 运行时闸门

在 provider 出口（`ChatSessionWriter` 之前）装一道形状校验：不合规的消息**直接报错**，
而不是静默流到前端由渲染层兜底。

校验器倾向手写，沿用仓库已有的 `readObjectRecord` / `readNonEmptyString` 读取器风格，
不引入新依赖。选 zod 这类库也可行，但它带来的收益主要在 schema 复用，
而这里的形状是本仓库自有的，复用面有限。

### 1c 判别联合

把 `NormalizedMessage` 从平铺可选字段改成按 `kind` 判别的联合：
`tool_use` 才有工具字段，`permission_request` 才有权限字段，取错字段编译期就拦。

这一片最大，走渐进路线：先按 kind 定义各自的载荷类型并导出收窄谓词，
新代码直接用，旧调用点分批迁移，不做一次性破坏式替换。**依赖 1a 先落地**。

### 1d 能力矩阵收口

后端 `provider-capabilities.catalog.ts` 是唯一真源，但前端另有一份硬编码
（`providerQuota.ts` 的 `QUOTA_PROVIDERS`）以及 20 处 `provider === 'xxx'` 裸分支。

矩阵扩到覆盖 quota、权限、计划文档、选择题、子代理，前端一律读矩阵。
做完之后「某家引擎没实现某能力」是矩阵里的一个 `false`，而不是一个 bug。

本片与消息类型无关，**可与 1a 并行**。

## 1a 的实施步骤

1. 建 `shared/protocol/`，放入协议类型：`NormalizedMessage`、`MessageKind`、
   `GatewayEventKind`、`ServerEventKind`、`SubagentActivity`、`SubagentInfo`、
   `MemoryCitation`、`SessionUpsertedEvent`、`SessionRemovedEvent`、配额形状等。
2. 逐字段裁决 15 个漂移项，写进协议或留在本端，每一项在类型注释里说明归属理由。
3. 删索引签名，补齐 38 处报错对应的声明。
4. 两端 `types.ts` 改为从协议 re-export，删除重复定义。
5. `npm run typecheck` 前后端全绿；`npx vitest run` 与 `npm test` 全绿。
6. 同步 `docs/core/providers.md`（协议归属）与 `docs/core/chat.md`（帧契约来源）。

## 1a 的验收

- 线上字段只有一处定义；前端的 `NormalizedMessage` 是它的派生类型，本地扩展显式列出而非另起一份
- `[key: string]: unknown` 从协议类型中消失
- 前后端 typecheck 全绿，前端 71 个测试文件与服务端测试全绿
- 新增一个协议字段若只改一端，typecheck **必须失败**（这是本片唯一要证明的能力）
