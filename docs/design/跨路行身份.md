# 跨路行身份（阶段 3）

> 状态：3b 已实施；3a 已回退（两路 id 空间不同）；3c 已盘点 zcode 与 claude
> 目标：让实时与历史两路靠**身份**对账，而不是靠时钟和文本相似度猜

## 现状勘察：标准在，但只有一家喂它

`NormalizedMessage.providerRowKey` 是协议为"同一行在两路上的身份"设计的字段，
文档写得很清楚：它是唯一不依赖时钟、也不依赖推断回合位置的跨路身份。

**全仓只有 antigravity 设置它。**

```
server/modules/providers/list/antigravity/antigravity-sessions.provider.ts   2 处
（其余五家：0 处）
```

于是 codex / cursor / opencode / zcode 的 assistant 文本对账，
**落到 `sessionMessageTurnDedupe.ts` 的启发式路径**，那里叠了两层猜：

1. **回合边界靠挂钟**——`allChronological = [...serverMessages, ...realtimeMessages].sort(compareMessagesChronologically)`，
   把两台机器的时间戳混排后找"前一条用户消息"。这正是阶段 0 从显示合并里拿掉的那件事，
   去重路径还留着。该文件的注释自己承认：clock skew 会把一条较旧的实时行挂到较新的持久化回合上。
2. **回合归属靠用户消息文本相等**——从后往前找 `content` 相同的服务端用户行。
   重复提示词（"继续"、"好"、"go on"）会绑到错误的回合。

最后由 `isAssistantTextMatch` 用「去空白相等」或「前缀且 `minLen >= 20` 且
（比例 ≥ 0.75 或 `minLen >= 100`）」判定是否同一行。

这就是"流式与非流式消息重复"反复出现的结构性原因：
**身份机制早就设计好了，但多数引擎没有喂它，前端只能猜。**

## Codex 两路不共享行身份

Codex 的两个传输各自编号，不在同一个 id 空间：实时 SDK 流按回合给 item 编号
（`item_0`、`item_1`），落盘 rollout 记的是模型响应 id（`msg_…`）。

因此 Codex **不设 key**。曾经给两侧各设自己的值，结果**比不设更糟**：对账走进身份分支、
找不到匹配、判定两行不同，于是回复渲染两遍，而因果回退被整个跳过。
这条教训记在 `codex-sessions.test.ts` 的"a Codex reply is left unkeyed"用例里。

**Claude 不需要 key：两路的行 id 本来就相等。** `SDKAssistantMessage.uuid` 与该行落盘后
JSONL 的 `uuid` 是同一个值，且 SDK 在完整消息模式下每条消息只带一个内容块，与转录"一块一行"
的粒度一致。归一化的 `baseId = raw.uuid` 因此在两路上取到同一个 uuid，产出的行 id 逐行相同，
`id` 本身即身份。claude runtime 不开 `includePartialMessages`，实时侧不产生流式行，
所以也没有需要靠正文对账的中间态。这条性质由 `providerLiveHistoryConformance` 的 claude
夹具钉住（夹具采自真实 run 的实时帧与同一会话的转录）。

## 切片

### 3b 去重路径改用因果锚点

把 `isAssistantTextEchoedInSameTurnOnServer` 里的挂钟混排换成阶段 0 已经建立的因果锚点，
与显示合并保持同一套口径。无身份可用的引擎仍需要它，但不该再由时钟裁决回合。

### 3c 其余引擎的身份盘点

**zcode：无可用行身份（已盘点，结论为否）。**
落盘侧的行身份是 `(message_id, part_id)`——历史查询 `LEFT JOIN part ON p.message_id = m.id`，
一条 message 可以有多个 part，归一化时每个 part 产出一行。
实时侧 `zcode-live-event-normalizer.ts` 的文本事件只拿得到 `payload.messageId`，
全模块 `part_id` 仅出现在历史 provider 的 SQL 里，实时协议从不下发。

因此 message 级 id 对行身份是 1:N：只有一个 part 时碰巧能用，多 part 时静默失效。
按协议要求（没有稳定原生身份就省略，不得用序号或本端生成值顶替），zcode **不设 key**，
继续走因果回退路径。

解锁条件在**引擎侧**：文本流事件带出 part id 即可——`tool_result` 事件已经带了
`resultPartId`，文本事件缺对应字段。适配器补不了。

**cursor / opencode：不投入。** 本 fork 的使用者不使用这两家引擎，
逐引擎的调研与适配不值得为它们花时间。跨引擎的统一改动（协议、能力矩阵、编译期约束）
仍然覆盖它们，保持可编译可通过测试。
